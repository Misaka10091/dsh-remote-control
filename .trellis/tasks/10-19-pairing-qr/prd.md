# 配对二维码：零依赖编码器与面板渲染

## 背景

父任务 `prd.md` D2 要求「二维码为主 + 纯文本码手输」，但实现阶段把它延期了：本包零运行时依赖（有测试守着），
一个 QR 编码器要自己写 Reed–Solomon 纠错、掩码选择、格式/版本信息 300+ 行，而「只能自己验证自己的编码器」
会产出最坏的东西——看起来像二维码但扫不出来。当时的取舍写进了 `README.md` / `CHANGELOG.md` / `src/client.js` 文件头。

结果是配对流程只有纯文本码（8 位 base32，分组显示）+ 可复制的一次性链接。用户 2026-10-19 提出「二维码怎么没了」——
它从未存在过，但 D2 确实承诺过，且手机端手输 8 位码 + 长链接明显不如扫一下。

研究（`research/qr-reference-vectors.md`）已确认：可以用**两个独立工具夹住自己**验证，
不需要引入运行时依赖，也不需要把配对码发给任何服务端。

## 目标

1. 面板在配对码旁渲染一个**真能扫**的二维码，内容是当前生效的配对链接。
2. 编码器零运行时依赖、纯函数、可被 `npm test` 逐位验证。
3. 验证强度分层且如实标注：与成熟实现逐位一致 → 独立解码器回读 → 手机实扫（人工）。
4. 不破坏既有安全设计：**配对码仍然不进任何请求**，二维码必须在浏览器侧生成。

## 范围

| # | 能力 | 说明 |
|---|---|---|
| R1 | QR 编码器 | byte 模式、纠错等级 M、版本自适应（1–15）、掩码按规范罚分自动选择；纯函数，挂在 `internals` 上供测试驱动 |
| R2 | 面板渲染 | 有配对码时在文本码上方渲染 SVG 二维码（静区、`crispEdges`、`role="img"` + 可读标签）；无 canvas、无网络请求 |
| R3 | 跟随接入地址 | 二维码内容 = 当前生效地址拼出的配对链接；切换局域网/公网地址后二维码**立即重绘**，配对码不作废 |
| R4 | 容量与失败 | 链接超出容量时给出明确提示（改用文本码 / 缩短公网地址），**绝不截断、绝不静默产出坏码** |
| R5 | 验证 | 逐位比对 fixture（参考实现 byte 模式 + 固定版本 + 8 个掩码）、自动版本/掩码比对、独立解码器回读、真机扫码 |

### 明确不在范围内

- **多模式分段优化**（数字/字母数字段混排）：能让符号更小，但会让「与参考实现逐位比对」失去意义（见研究 §3.1）。
  本实现只做 byte 模式，版本可能比最优解大 1–2 级，换来可预测与可验证。
- 二维码美化（logo、圆点、渐变、彩色）、纠错等级可调、静区尺寸可配。
- 宿主侧生成（`src/host/qr.js`）或任何「把链接发给服务端换图」的做法——理由见研究 §5。
- 扫码后自动跳转/自动配对（那是配对页已有的事）。

## 验收标准

1. `internals.encodeQr(text)` 对 fixture 中每条文本、每个固定掩码的输出矩阵，与参考实现（node-qrcode，强制 byte 模式，同版本同掩码）**逐位完全一致**。
2. 自动版本与自动掩码的输出，与参考实现的 byte 模式自动输出**逐位完全一致**；容量边界（v1 最小、v15 上限）各有一条断言。
3. 超出容量时返回可识别的失败（而不是抛异常或产出坏码），面板显示 `pair.tooLong` 提示，文本码与链接照常可用。
4. 面板在有配对码时渲染出二维码节点：`tests/client.test.mjs` 用 stub React 渲染 `PairingSection`，断言 SVG 存在、模块数量与编码器矩阵一致、`aria-label` 可读。
5. 二维码内容随选定接入地址变化：同一配对码下切到另一条地址，矩阵随之改变（且配对码字段不变）。
6. 零运行时依赖不变：`package.json` 无 `dependencies`/`devDependencies`，`src/client.js` 仍然只有一个 `__ModuleLoader__.load` 入口、无顶层 `import`/`export`、`require` 不越 baseline 白名单。
7. `npm test` 全绿（现有 533 + 新增），`npm run check:syntax` 通过，`npm pack --dry-run` 文件清单不变形。
8. **验证程度如实记录**：报告里必须区分「与参考实现逐位一致」「独立解码器回读通过」「真机扫码未验证/已验证」三件事，不得把前两者说成第三件。

## 关键约束

1. 客户端半边没有 DOM 测试环境（不引入 jsdom）——编码器必须是**纯函数**，渲染部分只做「有节点、模块数对得上」这种结构性断言。
2. 二维码内容含一次性配对码，因此**只能在浏览器里生成**；不得为生成图片而把链接 POST 给宿主 API（研究 §5）。
3. 面板此前已改为模态弹窗（任务 `10-19-panel-access-modes`），二维码要在该布局内不撑破面板：默认边长 ≤ 200px，窄视口自适应。
4. 参考实现与解码器只作为**一次性开发工具**装在 `%TEMP%`，不得进入 `package.json`；fixture 以纯文本 JSON 提交。

## 已定稿的决策

| # | 问题 | 决策 |
|---|---|---|
| D1 | 编码器位置 | 客户端半边（`src/client.js`，挂 `internals`），因为内容含配对码，不能发给宿主 |
| D2 | 编码模式 | 只做 byte 模式 + ECC M；不做多模式分段优化 |
| D3 | 版本范围 | 1–15（v15-M ≈ 412 字节，覆盖 253 字符域名的最坏链接）；超出明确报错 |
| D4 | 验证方式 | 参考实现逐位比对（固定掩码）+ 自动模式比对 + 独立解码器回读 + 人工真机扫码 |
