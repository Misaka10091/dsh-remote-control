# 研究：如何验证一个手写 QR 编码器

> 任务 `10-19-pairing-qr`（父任务 `10-17-remote-control` 的 `prd.md` D2）。
> 日期：2026-10-19。结论先行：**用两个独立工具（参考编码器 + 独立解码器）夹住自己**，
> 参考矩阵固定「byte 模式 + 版本 + 掩码」后逐位比对，回读用独立解码器，真机扫码单独标注。

## 1. 为什么不能自己验证自己

`src/client.js` 文件头写过的理由：只能自己验证自己的编码器，会产出最坏的东西——
**看起来像二维码但扫不出来**，用户无法区分是码错了还是网络错了。
所以本任务必须先拿到「不依赖本实现」的期望值。

## 2. 可用工具（都装在 `%TEMP%`，**不进仓库、不进 `package.json`**）

```bash
npm install --prefix "$env:TEMP/qr-ref" qrcode jsqr
```

- `qrcode`（node-qrcode）：成熟参考**编码器**，可 `create([{ data, mode: 'byte' }], { version, maskPattern, errorCorrectionLevel })`。
- `jsqr`：纯 JS **解码器**，喂 RGBA 位图即可回读文本，独立于编码路径。

实测（本机，2026-10-19）：

| 文本 | 字节 | node-qrcode 版本 | jsqr 回读 |
|---|---|---|---|
| `01234567` | 8 | v1 21×21 | EXACT |
| `HELLO WORLD` | 11 | v1 21×21 | EXACT |
| `http://192.168.9.77:3090/remote-control/pair#AbCdEfGhIjKl:7K3M9Q2X` | 66 | v5 37×37 | EXACT |
| `https://` + 200×`a` + 配对路径 | 250 | v11 61×61 | EXACT |

→ 编码器与解码器两条腿都可用，容量曲线也拿到了：**ECC M 下 66 字节要 v5，250 字节要 v11**。

## 3. 三个坑（都实测到了，直接决定测试怎么写）

### 3.1 参考实现会做「多模式分段」，逐位比对必须先固定 byte 模式

同一条 66 字节链接，node-qrcode 自动分段成 `Byte + Alphanumeric + Byte + Alphanumeric`
（数字段用 5.5 bit/字符），于是**塞进 v4（33×33）**；只用 byte 模式则要 **v5（37×37）**。
两者都是合法二维码，矩阵自然不同。

**做法**：fixture 一律用 `create([{ data: text, mode: 'byte' }], …)` 强制 byte 模式。
本实现也只做 byte 模式（不做分段优化），版本会略大于最优解，换来的是可预测与可验证。

### 3.2 掩码选择在实现之间不可靠，逐位比对必须钉死掩码

- node-qrcode 与 python-qrcode 在 byte 模式、同版本、同纠错等级下，**矩阵仍然不同**（66 字节那条差 558 格）。
- 对另一条文本，python 的矩阵恰好等于 node 在 **mask 2** 的结果；对 66 字节那条，**8 个掩码没有一个能对上**。

→ 掩码选择（罚分规则）在实现间有差异，不能当作跨实现不变量。
**做法**：
1. 逐位比对的 fixture 钉死 `version` + `maskPattern`（8 个掩码各一份），验证的是**数据编码 + RS 纠错 + 交织 + 功能图形 + 格式/版本信息 + 放置**；
2. 自动掩码/自动版本另用一条 fixture：与 node-qrcode 的 byte 模式**自动**输出比对；
3. 真正的兜底是 §4 的解码回读——掩码选哪个都不影响可扫性。

### 3.3 容量必须按 byte 模式算，不能按参考实现的自动结果算

最坏情况是用户填一个 253 字符的公网域名：链接 ≈ 300 字节。
byte 模式 + ECC M 下 250 字节已经是 v11，300 字节落在 **v12–v13**。
**做法**：版本表做到 v15（v15-M ≈ 412 字节，留足余量），超出容量**明确报错**，绝不截断或静默产出坏码。

## 4. 定稿的验证策略（四层，逐层独立）

| 层 | 手段 | 能证明什么 | 能否进 `npm test` |
|---|---|---|---|
| 1 | 与 node-qrcode 逐位比对（byte 模式 + 固定版本 + 8 个掩码） | 数据编码、RS 纠错、交织、功能图形、格式/版本信息、模块放置全对 | ✅ fixture 是纯文本 JSON |
| 2 | 与 node-qrcode 自动版本/掩码比对 | 版本选择与罚分规则与成熟实现一致 | ✅ |
| 3 | jsqr 回读本实现产出的矩阵 | **符号真的能被解码**（不依赖任何编码实现的正确性） | ❌ 需要 `jsqr` 依赖，零依赖约束不许；作为一次性验证记录在案 |
| 4 | 手机实扫 | 真实摄像头链路可用 | ❌ 人工，报告里如实标注 |

## 5. 一个被研究结论改掉的架构决定

**编码器放客户端，不放宿主。**

最初设想放 `src/host/qr.js`（Node 侧好测），但二维码要编码的是**配对链接**，而链接的 fragment 里带着
一次性配对码。本插件的既定设计是「配对码永远不进任何请求」（`design.md` §3.1：放在 fragment 里，
所以不会被写进访问日志）。若让面板把链接 POST 给宿主 API 去生成 SVG，就等于**为了让码更好看，把码发给了一个服务端**——
哪怕那是回环。这条不能破。

放客户端还有第二个好处：客户端半边的纯函数本来就是可测的——`tests/client.test.mjs` 已经用
`bundle.internals.*` 直接驱动 `pairingUrl` / `classifyFailure` 等函数，编码器同样挂在 `internals` 上即可逐位断言。
