# 远程控制插件：配对鉴权与设备管理

## 背景

`dsh web` 只监听 `127.0.0.1`，手机或另一台电脑无法接入同一会话，人在离开工位时 agent 就断了可观测、可干预的通道。

社区已有两套方案（`april-jk/dsh-mobile-plugin`、`zhu1090093659/dsh-web` 的 `dsh-remote-web-ui`），共同点是**只解决"谁能进"，没有解决"进来以后能做什么"**：

- `dsh-mobile-plugin` 走自建 Relay 中转，引入一个外部信任方，且需要额外部署（[#2520](https://github.com/deepseek-ai/deepseek-harness/discussions/2520)）。
- `dsh-remote-web-ui` 走 `/remote/api` 配对门控，配对令牌一次性、可吊销，但**已配对设备即获得完整操作权**，没有按设备的能力边界。
- 官方侧 `dsh web` 的 `127.0.0.1` 校验是硬约束，多个接口拒绝 `--trusted-host` 传入的域名（[#351](https://github.com/deepseek-ai/deepseek-harness/discussions/351)）。

本项目要做的是**复用 dsh 已有 Web 能力 + 自己加鉴权层 + 设备管理面板**，不引入 Relay、不依赖第三方中转、不直连公网。

## 目标

1. 手机/平板/另一台电脑能在同一局域网内打开与桌面**同一个** DSH 会话，正常收发消息、查看流式输出、响应审批。
2. 未经配对授权的请求一律不可用，且这是默认行为——不开启远程能力时行为与原生 `dsh web` 完全一致。
3. 用户能在侧边栏底部常驻入口看到"当前有哪些设备连着、它们做了什么"，并能一键吊销。
4. MVP 先跑通"能连、能管、能审计"，按设备的能力细分留到后续版本。

## 范围（MVP）

### 交付物

| # | 能力 | 说明 |
|---|---|---|
| R1 | 可选的局域网监听 | 显式开启后才把监听地址从 loopback 切到局域网；未开启时零行为变化 |
| R2 | 配对流程 | 桌面端生成一次性配对码/二维码；远程设备凭码换取设备令牌 |
| R3 | 请求鉴权网关 | 未携带有效设备令牌的远程请求被拦截；桌面本机回环访问不受影响 |
| R4 | 设备管理面板 | 侧边栏底部常驻图标，列出已授权设备的名称、最后在线、来源地址，支持即时吊销 |
| R5 | 操作审计 | 本地 JSONL 记录远程设备的连接、消息、吊销等关键动作，可导出，默认保留 30 天 |
| R6 | 移动端可用性 | 远程接入时界面可正常使用（至少会话列表、对话、输入、停止） |

### 明确不在 MVP 内

- 按设备的能力白名单（只读 / 发消息 / 审批应答 / 管理）——**架构上预留，MVP 不实现**，所有已配对设备等价。
- 自建 Relay、公网穿透、内网打洞。外网场景靠用户已有的 Tailscale / Cloudflare Tunnel 等方案，本项目不内置。
- 端到端加密应用层载荷。
- 原生 `dsh web` 的移动端 CSS 修复（属于上游问题，本项目只保证接入后可用，不重构官方布局）。
- 多机编排（一个 DSH 控制多台机器的 DSH）。

## 关键约束

1. **默认安全**：远程能力默认关闭；关闭时插件不得改变 `dsh web` 的任何可观测行为。
2. **不引入外部信任方**：不依赖任何第三方 Relay 或云服务。
3. **不直连公网**：MVP 只面向局域网/私有网络（含 Tailscale 这类已建立的私有组网）。
4. **不破坏本机体验**：回环访问、官方 CLI 与桌面客户端的既有路径不得要求配对。
5. **吊销必须即时生效**：吊销后该设备的新请求立刻被拒，已建立的连接被关闭。
6. **升级韧性**：鉴权放在入口层按路径前缀拦截，不逐个改写 DSH 内部接口；DSH 版本升级时不需要跟进内部 API 变更。
7. **署名与隐私**：仓库与提交不得出现公司邮箱等私人信息（已配置 noreply 身份）。

## 已确认的技术前提

- `@deepseek-ai/dsh-host-webserver` 的 `WebServer.Config.host` 取值为 `127.0.0.1` 或 `0.0.0.0`，`port` 可为 `0`（由 OS 分配）。
- 该服务提供 `register({ kind, path, handler })`（`exact` / 前缀）、`registerUpgrade({ path, handler })`、`registerFallback(handler)`。
- 现有路由注册后请求**直接进入 handler**，WebServer 本身没有请求拦截钩子——鉴权必须自己实现。
- `ctx.authorization` 是为"与用户对话获取凭证"设计的，**不适用于请求鉴权**，因此网关层自行实现。
- 插件通过 `dsh.bundle.patch` 安装，客户端通过 `dsh.client` 注入注册 UI，形态与 `dsh-git-panel` 一致。

## 已定稿的决策

以下问题已在需求讨论中定稿，技术设计按此展开：

| # | 问题 | 决策 |
|---|---|---|
| D1 | 监听架构 | **方案 B**：插件自建独立监听端口做反向代理，官方 `dsh web` 保持 `127.0.0.1` 不变。默认安全优先，官方端口完全不对外。 |
| D2 | 配对码形式 | **二维码为主 + 纯文本码手输**。一次性、短有效期。 |
| D3 | 鉴权凭证 | **HttpOnly Cookie（SameSite=Lax）+ Origin 校验**，覆盖页面导航、API、WebSocket 三类请求。 |
| D4 | 令牌存储 | 桌面端存 `~/.dsh/remote-control/devices.json`，权限 0600。不用 OS 凭据存储（MVP 成本考量）。 |
| D5 | 审计粒度 | 连接、发送消息、停止任务、审批应答、吊销——**记录动作与时间，不记消息正文**。 |
| D6 | 能力白名单 | **MVP 不实现**，所有已配对设备等价；数据结构与网关判定点预留扩展位。 |

### 由此产生的架构要求

- 代理层必须自行承载 WebSocket 长连接：官方流式通道是 `ws` 在 `/api/remote.mux` 上的多路复用连接（`WebSocketServer({ noServer: true })` + `handleUpgrade`），HTTP 反向代理无法透传。
- 官方 WebServer **不做 Origin 或 Host 校验**，所以 Origin 校验必须由我们的网关负责，否则远程页面可被任意站点跨站发起请求。
- 由于官方端口保持 loopback，插件自建端口是唯一对外入口，**未配对请求在到达 DSH 之前就被拒绝**，不依赖对官方内部接口的覆盖完整度。

## 验收标准

- [ ] 未开启远程能力时，`dsh web` 行为与未安装插件一致。
- [ ] 开启后，局域网内另一台设备通过配对码成功接入，能打开并操作同一会话。
- [ ] 未配对设备访问远程入口时被拦截，且不泄露会话内容。
- [ ] 设备管理面板能正确列出已授权设备及其最后在线时间。
- [ ] 吊销某设备后，该设备的后续请求立即失败，已有连接被断开。
- [ ] 审计记录可在本地查看与导出，过期后按 30 天策略清理。
- [ ] 本机回环访问全程不需要配对。
- [ ] 仓库内与提交历史中不含公司邮箱等私人信息。
