# @misaka10091/dsh-remote-control

**给 `dsh web` 加一层配对门控的远程接入：手机或局域网里的另一台电脑可以打开同一个会话，附带设备管理面板与本地审计。没有中转，没有第三方服务。**

## 为什么需要它

`dsh web` 只监听本机回环地址，一离开工位，agent 就既不可观测也无法干预。常见做法要么把流量绕经外部中转（一个你必须信任的第三方），要么让每台配对设备拿到完整权限、以后想收紧都没有边界。

这个插件选了第三条路：

- **官方端口始终留在回环。** 插件自己开一个监听，作为唯一的远程入口；本机访问不经过它，所以没开远程接入时，行为与原生 `dsh web` 完全一致。
- **未配对的请求到不了 DSH。** 拒绝发生在插件这一层，不是靠 DSH 自己兜。
- **一个只做鉴权的反向代理。** 它不理解 DSH 内部，所以 DSH 升级不会把它弄坏。

## 功能

- **配对式接入** — 面板里生成一次性配对码，有效期 120 秒；扫码或打开链接即可完成配对。
- **设备面板** — 侧栏底部入口，顶部是总开关与端口，四个 tab：配对 / 接入 / 设备 / 审计。
- **接入地址簿** — 局域网网卡或你自己配置的公网地址，可增删、备注、标出使用中。
- **设备管理** — 查看已配对设备与最后活跃时间，随时吊销（即时生效，含在线连接）。
- **本地审计** — 谁在什么时候做了什么，按天记录、保留 30 天、可筛选、可导出；不记录消息正文。
- **零运行时依赖** — 不需要额外安装任何东西。

## 安装

```bash
dsh plugin --profile web add @misaka10091/dsh-remote-control
```

装本地 checkout（未发布的改动）：

```bash
dsh plugin --profile web add link:/absolute/path/to/dsh-remote-control
```

> 用 CLI profile（如 `web`）。`desktop` profile 由桌面应用托管，会拒绝 CLI 插件命令。

装好后侧栏底部出现「远程连接」入口（若没有，重启 dsh 再刷新页面）。

## 快速开始

1. 打开侧栏底部的**远程连接**面板，在顶部打开总开关，确认端口。
2. 在「配对」tab 里选好接入地址，点**生成配对码**。
3. 用手机相机扫旁边的二维码，或在设备上打开同一个链接，也可以直接输入文本码。
4. 配对成功后浏览器会带着凭证回到会话页——这台设备之后就是一个正常的远程入口。
5. 想收回权限：在「设备」tab 里吊销。想彻底关闭：关掉顶部总开关，或停用插件。

## 工作原理

```
手机 / 局域网电脑  ──►  插件网关（配对 + 鉴权 + 反向代理）  ──►  dsh web（仅回环）
                              │
                              └──►  本地审计日志（谁、何时、做了什么）
```

- 配对阶段：一次性码换一个**签名的、有期限的设备凭证**，由设备自己持有（HttpOnly、`SameSite=Lax`）。
- 之后的每个请求：校验凭证 → 校验来源（阻止跨站写入）→ 校验是否已被吊销 → 才转发给 DSH。
- 吊销不依赖凭证自己过期：服务端保留一份吊销集合，改完立刻对下一个请求生效。

## 安全边界（务必读）

这是 MVP，下面这些限制是**刻意的**。写出来而不是藏起来，因为它们决定这个插件是否适合你。

1. **没有传输加密。** 网关在局域网上说的是明文 HTTP；同一网段的被动监听者可以读到会话流量。要 TLS 就在前面放自己的反向代理，或用 Tailscale 一类的私有组网——插件不内置任何一种。
2. **设备凭证就是完整控制权。** 所有配对设备等价，还没有按设备的能力白名单。凭证被盗用即等于该设备的全部权限，没有第二因子；提前结束它的唯一方式是**吊销**（或等它到期，默认 30 天）。
3. **签名密钥在磁盘上，那就是信任锚。** 能读插件数据目录的本机攻击者可以伪造任意设备凭证——这与「本机账户已被攻破」是同一信任级别。密钥刻意持久化：内存密钥会工作到下次重启，然后静默地让所有设备失效。
4. **挡得住跨站写，挡不住同站 XSS 和本机恶意程序。** 同源校验针对的是别的网站伪造你的请求，不是已经在你页面里或你机器上运行的代码。
5. **吊销只面向未来。** 它会拒绝新请求并关闭在线连接，不会撤销已经做完的动作。
6. **本机访问不经过网关鉴权**，但要同时满足回环连接与回环地址两条，只有一条不算（这正是 DNS rebinding 能伪造出来的东西）。
7. **配对入口按设计无凭证可达。** 正在配对的设备还没有凭证；这个豁免只豁免凭证，配对页仍然过同源校验、仍然遵守总开关、仍然受限速约束，也从不接触 DSH。
8. **猜码是限速的，不是不可能的。** 错码会销毁当前配对码，并按来源地址封禁；这只是让无效搜索又吵又慢，不能让「泄露后猜中」变成不可能。
9. **关掉就等于消失。** 关闭插件或结束进程会关闭监听，不留下任何端口。
10. **官方端口的内层凭证从不离开服务器。** 它等价于整台 DSH 实例的完整访问权，只存在于「插件 → 官方端口」这一跳，不发给客户端、不写日志、不进审计。

## 数据与配置

所有状态都在本机，没有云端账号：

| 内容 | 位置 | 说明 |
|---|---|---|
| 设备表与设置 | `~/.dsh/remote-control/devices.json` | 权限 `0600`，原子写 |
| 签名密钥 | `~/.dsh/remote-control/jwt-key` | 首次使用时生成，`0600`；删掉它等于让所有设备失效 |
| 审计记录 | `~/.dsh/remote-control/audit-YYYY-MM-DD.jsonl` | 按 UTC 分天，保留 30 天 |

**不持久化任何凭证。** 设备凭证在设备手里，文件里只有设备行——比「只存摘要」更强。

设置项（是否启用、端口、接入地址簿）通过面板读写；`devices.json` 损坏时远程接入会拒绝启动并报错，而不是当成一张空设备表——那会表现为「所有设备都悄悄失效，而远程接入还在运行」。

## 发布

发布由 **git 标签**触发，通过 GitHub OIDC 发布到 npm 并创建带同一个 `.tgz` 的 GitHub Release，仓库里不保存任何发布凭据。

操作手册见 [`docs/RELEASING.md`](./docs/RELEASING.md)：**先读它的第一节**——`0.1.0` 是手工首发的（npm 上的包必须先存在，才能配置自动发布），从下一个版本起才是推标签即发布。文档里同时写清了这条链路哪些部分能在本地验证、哪些不能。

## 状态

- 已实现并测试：设备存储、配对码与二维码、签名设备凭证、HTTP 网关（监听 / 鉴权 / 同源校验 / 反向代理）、WebSocket 升级代理、管理 API 与审计、客户端面板（配对 / 接入 / 设备 / 审计）。
- **尚未验证：真机链路**——用手机完整走一遍「扫码 → 打开会话 → 发消息 → 收流式输出 → 停止」。这套测试覆盖不了的硬件部分是目前唯一剩下的工作。
- 同样尚未发生的还有一次真实的标签发布：发布自动化的规则可单测、脚本可干跑，但端到端链路没有被真跑过，文档不会把它写成已验证。
- 二维码的自动化验证是「参考编码器逐位比对 + 独立解码器回读」，**不是摄像头**——还没被任何真机扫过。
- 从 `0.1.0` 之前的开发版升级：旧凭证不被接受，所有设备需要重新配对一次（设备名与历史保留）。
